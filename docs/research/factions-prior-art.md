# Factions plugin prior art: architecture patterns and known pitfalls

Resolves GitHub issue #4 (research). Written 2026-09-16 against the pinned target **Paper 26.1.2 / Java 25**.

Scope: what `avian-factions` (SPEC §7–11, §25) should copy as a *pattern* and what it must avoid, derived from the source code and issue trackers of the open-source factions plugins. We take patterns only, never code; see the licensing note at the end (every studied repo with a licence is GPL-3.0 except AlpineFactions, which is MPL-2.0, and FactionsX, which has **no licence at all**).

## TL;DR

1. **Claims: in-memory, per-world, primitive-keyed.** Every plugin that performs well keeps chunk→faction in a heap map and only touches storage on change. The best design (FactionsUUID 4.x `WorldTracker`) is a per-world `Long2IntMap` keyed by a Morton-packed chunk coordinate, with a reverse `Int2ObjectMap<LongSet>` index for faction→claims. The worst (ImprovedFactions) runs a SQL `SELECT` per event, per block, and has open "extreme lag" tickets to show for it.
2. **Explosions: evaluate per distinct chunk, not per block.** FactionsUUID collapses `blockList()` to distinct chunks, evaluates each chunk once, then filters blocks by chunk. Plugins that decide per block (FactionsX, ImprovedFactions, Medieval) allocate a key object and do a lookup per block per explosion.
3. **Power: lazy, timestamp-based, per player.** FactionsUUID/Saber/FactionsX store `power` + `lastPowerUpdateTime` and apply regen/offline-decay on read; faction power is `sum(members)` computed on demand. No plugin scans all factions per tick. MassiveCraft's periodic task has a `return`-instead-of-`continue` bug that silently stops regen for the rest of the online list.
4. **Persistence is where data-loss bugs live.** Legacy FactionsUUID/Saber write whole JSON files non-atomically (`FileOutputStream` truncate-then-write); on next boot an empty `factions.json` is treated as "no factions", every player's faction is reset and the board cleaner drops every claim. Saber's MySQL backend does `DELETE FROM factions` + re-insert of *everything* on every autosave, from an async thread, over live mutable objects. Medieval Factions blocks the main thread on a DB upsert in `PlayerQuitEvent` (watchdog kill) and has a tautological optimistic-lock guard.
5. **Protection surface gaps are the most common bug class in every tracker**: sticky pistons pulling across borders, armor stands/item frames, projectiles, silverfish, wind charges, end crystals, hoppers across chunk borders, signs in safezones, buckets, dispensers, fire spread, frost walker. The consolidated checklist below lists 60+ events with who hooks what; Avian should hook the union.

## Per-plugin findings

### FactionsUUID, legacy line (drtshock/Factions 1.6.x)

**Claim storage.** `MemoryBoard.MemoryBoardMap extends HashMap<FLocation, String>` with a Guava `HashMultimap<String, FLocation> factionToLandMap` reverse index maintained in `put`/`remove` ([MemoryBoard.java L42-L97](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/data/MemoryBoard.java#L42-L97)). Wilderness is faction id `"0"`; missing key → `"0"` ([L104-L110](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/data/MemoryBoard.java#L104-L110)). `FLocation` is a `(worldName, x, z)` object whose `hashCode` is `(x << 9) + z + worldName.hashCode()` ([FLocation.java L247-L250](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/FLocation.java#L247-L250)) — every lookup allocates an `FLocation` and hashes a string. Faction ids are `String`s, so each lookup is a second `HashMap<String, Faction>` lookup in `Factions.getFactionById`. Oddly, `getAllClaims(factionId)` ignores the reverse index and scans the whole map ([L150-L158](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/data/MemoryBoard.java#L150-L158)).

**Explosions.** `AbstractListener.handleExplosion` first checks the explosion origin chunk, then maps `blockList()` to *distinct chunks*, evaluates `explosionDisallowed(boomer, chunk)` once per chunk and finally `blockList.removeIf(block -> !chunks.contains(block.getChunk()))` ([AbstractListener.java L98-L111](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/listeners/AbstractListener.java#L98-L111)). The decision function branches on boomer type (creeper / fireball+wither / TNT+minecart / other) × territory type (wilderness / normal-online / normal-offline / warzone / safezone) ([L151-L183](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/listeners/AbstractListener.java#L151-L183)). "Online" means `faction.hasPlayersOnline()`, which iterates online players. Note `chunks.contains` on a `List` is O(chunks) per block; fine for TNT (≤ a few chunks) but a `List` where a `Set` was meant. There is also the "TNT waterlog" anti-waterwall rule that breaks the six blocks around a TNT that detonates in liquid ([L113-L148](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/listeners/AbstractListener.java#L113-L148)) — relevant to SPEC §26 "water protection if configured".

**Power.** Per player: `power`, `powerBoost`, `lastPowerUpdateTime`. `getPower()` calls `updatePower()`, which (a) if offline applies `losePowerFromBeingOffline()` (loss per day × elapsed, floored at `offlineLossLimit`) and returns unless offline regen is on; (b) skips if the faction is power-frozen, the player is AFK (Essentials hook) or dead; (c) otherwise adds `elapsedMillis × powerPerMinute / 60000` clamped to `[min+boost, max+boost]` ([MemoryFPlayer.java L595-L665](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/data/MemoryFPlayer.java#L595-L665)). Faction power is `sum(fplayer.getPower())` over members, capped at `factionMax`, plus faction `powerBoost` ([MemoryFaction.java L629-L642](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/data/MemoryFaction.java#L629-L642)). No scheduled task touches power at all; `/f top`-style callers pay O(members) per faction. Death loss is applied in `onDeath()` (EntityDeathEvent monitor). The land-vs-power comparison for claim limits and raidability lives in `landraidcontrol/PowerControl` (with a DTR alternative), i.e. the "is raidable" rule is pluggable.

**Relations.** `Relation` enum `MEMBER > ALLY > TRUCE > NEUTRAL > ENEMY` with an int `value`; each faction stores `Map<String, Relation> relationWish`. Effective relation = whichever wish is *less friendly*: `if (fme.wish(fthat).value >= fthat.wish(fme).value) return fthat.wish(fme); else return fme.wish(fthat)` ([RelationUtil.java L56-L84](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/util/RelationUtil.java#L56-L84)). Same faction → `MEMBER`; system factions or peaceful flag → `NEUTRAL`. Protection checks call `faction.getRelationTo(player)` then compare with `isAtLeast(...)`; the per-faction `/f perms` matrix indexes by `Relation` and `Role` selectors. Enemy declaration is unilateral (one enemy wish wins), ally/truce need both.

**Persistence.** `SaveTask` runs on a *sync* repeating task every `saveToFileEveryXMinutes` (default 30) and calls `forceSave(false)` on factions, players, board ([FactionsPlugin.java L450-L452](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/FactionsPlugin.java#L450-L452), [SaveTask.java](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/data/SaveTask.java)). `JSONBoard.forceSave` builds a `Map<world, TreeMap<"x,z", id>>` and calls `gson.toJson` **on the main thread**, then `DiscUtil.writeCatch(file, json, sync=false)` writes the string from a Bukkit async task under a per-file lock ([JSONBoard.java L66-L69](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/data/json/JSONBoard.java#L66-L69), [DiscUtil.java L64-L100](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/util/DiscUtil.java#L64-L100)). The write itself is `new FileOutputStream(file); out.write(bytes)` — **truncate-then-write, not atomic** ([DiscUtil.java L37-L44](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/util/DiscUtil.java#L37-L44)). Boot order: load players → load factions → every player whose faction id is unknown gets `resetFactionData()` → load board → `Board.clean()` removes claims whose faction id is unknown ([FactionsPlugin.java L455-L467](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/FactionsPlugin.java#L455-L467)). `JSONFactions.loadCore` treats an **empty file as "no factions"** rather than an error ([JSONFactions.java L86-L94](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/data/json/JSONFactions.java#L86-L94)). Put together: a crash during the 30-minute save leaves a truncated `factions.json`; on restart all members are reset and all claims are cleaned, and the next autosave makes it permanent. A malformed (non-empty) file throws instead, which is safer. Issue [#1403 "Power resets when server restarts"](https://github.com/drtshock/Factions/issues/1403) and Saber's [#159](https://github.com/SaberLLC/Saber-Factions/issues/159)/[#160](https://github.com/SaberLLC/Saber-Factions/issues/160) ("factions disappear after restart", "Removing dead factions") are this family.

**Protection listener surface** (class → events):
- `FactionsBlockListener`: `BlockBreakEvent`, `BlockPlaceEvent`, `BlockDamageEvent`, `BlockFormEvent`, `BlockFromToEvent` (liquid flow across borders), `BlockPistonExtendEvent`, `BlockPistonRetractEvent` (sticky only), `BlockDispenseEvent`, `EntityBlockFormEvent` (frost walker).
- `FactionsEntityListener`: `EntityExplodeEvent`, `EntityDamageEvent` (+ `EntityDamageByEntityEvent` via `instanceof`, projectiles resolved to shooter, item frames/armor stands/paintings mapped to a "use block" check), `EntityDamageEvent` at MONITOR, `EntityDeathEvent` (power loss), `EntityCombustByEntityEvent` (flame arrows), `PotionSplashEvent` (harmful effects only), `EntityChangeBlockEvent` (enderman, wither), `EntityTargetEvent`, `CreatureSpawnEvent`, `HangingBreakEvent`, `HangingPlaceEvent`.
- `FactionsPlayerListener`: `PlayerInteractEvent` (materials.json "use" list, physical/pressure plates), `PlayerInteractEntityEvent`, `PlayerBucketEmptyEvent`, `PlayerBucketFillEvent`, `PlayerMoveEvent`, `PlayerTeleportEvent`, `PlayerCommandPreprocessEvent` (territory command deny), `PlayerJoinEvent`/`PlayerQuitEvent`/`PlayerKickEvent`/`PlayerLoginEvent`, `PlayerRespawnEvent`, `PlayerChangedWorldEvent`, `PlayerGameModeChangeEvent`, GUI events.
- `FactionsExploitListener`: `PlayerTeleportEvent` (ender pearl through walls), `BlockFromToEvent` (obsidian generators).
- `OneEightPlusListener`: `BlockExplodeEvent`, `PlayerArmorStandManipulateEvent`. `OneFourteenPlusListener`: `PlayerTakeLecternBookEvent`. `PortalListener_114`: `PortalCreateEvent`.

Missing from this line: fire spread (`BlockIgniteEvent`/`BlockBurnEvent`/`BlockSpreadEvent`), hoppers (`InventoryMoveItemEvent`), vehicles, end crystals, sign editing, silverfish (fixed later, [#1443](https://github.com/drtshock/Factions/issues/1443)), projectile griefing ([#1375](https://github.com/drtshock/Factions/issues/1375), still open).

**Paper 26.1.2 compatibility notes.** This line would not compile against paper-api 26.1.2: `PotionEffectType.CONFUSION/HARM/SLOW/SLOW_DIGGING` ([FactionsEntityListener.java L192](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/listeners/FactionsEntityListener.java#L192)) no longer exist (now `NAUSEA/INSTANT_DAMAGE/SLOWNESS/MINING_FATIGUE`, [PotionEffectType.java @ ver/26.1.2](https://github.com/PaperMC/Paper/blob/ver/26.1.2/paper-api/src/main/java/org/bukkit/potion/PotionEffectType.java)); it constructs synthetic `new EntityDamageByEntityEvent(damager, damagee, DamageCause.FIRE, 0d)` to reuse its damage check ([L186](https://github.com/drtshock/Factions/blob/c0104c1666/src/main/java/com/massivecraft/factions/listeners/FactionsEntityListener.java#L186), also MassiveCraft `EngineCanCombatHappen` L55/L75) and that constructor is `@Deprecated(since="1.20.4", forRemoval=true)` in favour of `DamageSource` ([EntityDamageByEntityEvent.java @ ver/26.1.2 L20-L41](https://github.com/PaperMC/Paper/blob/ver/26.1.2/paper-api/src/main/java/org/bukkit/event/entity/EntityDamageByEntityEvent.java#L20-L41)). Lesson: never build fake events to reuse a check; put the decision in a plain function that takes `(actor, target, location)`.

**Issue-tracker bug classes 2019-2023** (tracker moved to FactionsU/UID in 2022, [#1466](https://github.com/drtshock/Factions/issues/1466)): protection gaps ([#1293 sticky pistons pull from outside claims](https://github.com/drtshock/Factions/issues/1293), [#1277 armor stands/item frames](https://github.com/drtshock/Factions/issues/1277), [#1375 projectiles break item frames/minecarts/pressure plates](https://github.com/drtshock/Factions/issues/1375), [#1377 "other" explosion types not covered for offline/peaceful](https://github.com/drtshock/Factions/issues/1377), [#1443 silverfish infest blocks in peaceful land](https://github.com/drtshock/Factions/issues/1443), [#1393 piston machines across allied borders](https://github.com/drtshock/Factions/issues/1393)); state bugs ([#1403 power reset on restart for factionless players](https://github.com/drtshock/Factions/issues/1403), [#1363 faction bank clearing for no reason](https://github.com/drtshock/Factions/issues/1363) — closed as unreproducible); integration breakage (chat plugins, PlaceholderAPI, MythicMobs non-damaging spells [#1430](https://github.com/drtshock/Factions/issues/1430)).

### FactionsUUID 4.x (FactionsU/UID) — the actively-maintained modern successor

Same author lineage, rewritten packages (`dev.kitteh.factions`), GPL-3.0, Java 21+, Paper-first with a Spigot shim.

**Claim storage.** `MemoryBoard` holds `Object2ObjectMap<String worldName, WorldTracker>` ([MemoryBoard.java L50-L67](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/data/MemoryBoard.java#L50-L67)). `WorldTracker` is `Long2IntMap chunkToID` (default return `Integer.MIN_VALUE` = no match), `Int2ObjectMap<LongSet> IDToChunk`, and `Long2LongMap chunkToInhabited` (chunk inhabited-time cache fed by `ChunkLoadEvent`) ([WorldTracker.java L24-L100](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/util/WorldTracker.java#L24-L100)). Keys are Morton-interleaved `(x,z)` longs; faction ids are `int`s. Zero boxing, zero string hashing, and `FLocation` is now a `record` used only at the API edge ([FLocation.java L19](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/FLocation.java#L19)). `factionAt()` is: world map lookup → long map lookup → `Factions.get(int)`, falling back to the wilderness singleton. This is the design to copy.

**Explosions.** Identical distinct-chunk algorithm as legacy, plus: `ExplosionResult.TRIGGER_BLOCK` + `WindCharge` → filter blocks by the shooter's use-block permission; blast resistance ≥ 100 (via `Material.getBlastResistance()`) replaces the hard-coded material list; grace period disables the waterlog rule ([ListenExplode.java](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/listener/ListenExplode.java)). Decision logic is centralised in a static `Protection` class: `denyBuildOrDestroyBlock`, `denyExplode`, `denyInteract`, `denyUseBlock`, `denyUseItem`, `denyDamage` ([Protection.java](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/protection/Protection.java)), with a `testFactionType(faction, online, ifNormal, ifNormalOffline, ifWilderness, ifSafeZone, ifWarZone)` table lookup ([L208-L218](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/protection/Protection.java#L208-L218)). Listeners are thin: they translate the event into a `deny*` call and cancel.

**Power.** Same lazy timestamp model ([MemoryFPlayer.java L643-L690](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/data/MemoryFPlayer.java#L643-L690)); faction `power()` sums members on demand ([MemoryFaction.java ~L1075-L1085](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/data/MemoryFaction.java#L1075-L1085)); `hasMembersOnline()` still iterates `getOnlinePlayers()` ([L1327-L1339](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/data/MemoryFaction.java#L1327-L1339)) — cheap enough but called from every explosion decision; a per-faction online-member counter maintained on join/quit would be O(1). Time-of-day scheduling (raid shields, SPEC §27) is done from Paper's `ServerTickEndEvent` by bucketing `LocalTime` to half-hours and only doing work when the bucket changes ([ListenTiming.java](https://github.com/FactionsU/UID/blob/bc9ed70fc5/paper/src/main/java/dev/kitteh/factions/listener/ListenTiming.java)).

**Relations.** `ConcurrentHashMap<Integer, Relation> relationWish` ([MemoryFaction.java L393](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/data/MemoryFaction.java#L393)); same "less friendly wish wins" rule; permissions use `RelationAtLeastSelector`/`RoleAtLeastSelector`/`PlayerSelector`/`FactionSelector` objects so a claim's access list is a small ordered list of selectors rather than a matrix.

**Persistence.** Same 30-minute cadence, but `JSONFactions.forceSave` snapshots (`new ArrayList<>(factions.values())`), serialises **on the calling (main) thread** ("Serialize sync, write (a)sync") and hands a `Supplier<String>` to `JsonSaver`, which writes to `<file>.tmp` and `Files.move(..., REPLACE_EXISTING, ATOMIC_MOVE)` under a per-path lock ([JsonSaver.java L20-L57](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/data/json/JsonSaver.java#L20-L57), [JSONFactions.java L42-L50](https://github.com/FactionsU/UID/blob/bc9ed70fc5/bukkit/src/main/java/dev/kitteh/factions/data/json/JSONFactions.java#L42-L50)). Caveat: `JSONBoard` and `JSONFPlayers` pass `() -> gson.toJson(map)` so their serialisation runs on the async thread over a map built on the main thread (safe for the board because `dumpAsSaveFormat()` copies; for players the list holds live `JSONFPlayer` objects, so a field mutated mid-serialisation can tear). Database support is an open, explicitly-deferred ticket ([UID#23](https://github.com/FactionsU/UID/issues/23)).

**Listener surface** (`ListenBlock`: BlockBreak/Place/Damage/Form/FromTo/Dispense, EntityChangeBlock (enderman, silverfish, wither, ...), EntityBlockForm, HangingBreak/Place; `ListenPiston`: extend/retract; `ListenExplode`: Block/EntityExplode; `ListenDamage`: EntityDamage (+ByEntity), Combust, Death, PotionSplash, respawn-invulnerability, territory damage boost/resistance upgrades; `ListenInteract`: PlayerInteract, PlayerInteractEntity, ArmorStandManipulate, BucketEmpty/Fill, SignChange, TakeLecternBook; `ListenMove`: Move/Teleport; `ListenEnderPearl`; `ListenPortal`: PortalCreate; `ListenSpawn`: CreatureSpawn, EntityTarget; `ListenCommandDeny`; `ListenChunks`: ChunkLoad; `ListenUpgrade`: BlockGrow, BlockDropItem, SpawnerSpawn, EntityDeath, PlayerItemDamage, FoodLevelChange; Paper-only `ListenPaperBeacon`: BeaconEffectEvent, `ListenPaperChat`: AsyncChatEvent, `ListenTiming`: ServerTickEndEvent). Still no fire-spread or hopper hooks.

**Bugs 2023-2026** ([full list](https://github.com/FactionsU/UID/issues?q=is%3Aissue)): [#42 anyone can edit signs in safezones](https://github.com/FactionsU/UID/issues/42) (the check short-circuited before reaching the safezone branch; maintainer: "This is why you don't edit, test, edit again, and fail to test before publishing"); [#55 cannot open containers in wilderness](https://github.com/FactionsU/UID/issues/55) (regression from the permission rewrite — nobody had a test for wilderness); [#41 `/f unclaimall` not updating power/claim count](https://github.com/FactionsU/UID/issues/41) (reverse index out of sync); [#46 FTOP money takes 4 s on the main thread](https://github.com/FactionsU/UID/issues/46) (Vault balance lookups per member, fixed with caching in 4.6.0); [#25 Graves integration broke on a minor version](https://github.com/FactionsU/UID/issues/25). Pattern: every regression was in the *decision function*, not in storage, and none had a unit test.

### SaberFactions (SaberLLC/Saber-Factions)

Fork of FactionsUUID 0.5 with a large feature pile (missions, shop, alts, grace, Discord, audit, F-top, TNT bank, chunk busters). Same GPL-3.0 licence text as FactionsUUID.

**Claims.** `MemoryBoard` is FactionsUUID's with `flocationIds.getOrDefault(flocation, "0")` and a `getFactionClaims(id)` reverse index ([MemoryBoard.java](https://github.com/SaberLLC/Saber-Factions/blob/aa523f90ab/factions-shared/src/main/java/com/massivecraft/factions/zcore/persist/MemoryBoard.java)). `setFactionAt` is wrapped in `getScheduler().runRegion(...)` (Folia-style scheduler abstraction) and each change calls `EngineDynmap.requestUpdate()`. Dynmap rendering was a documented lag source ([#140](https://github.com/SaberLLC/Saber-Factions/issues/140)).

**Power.** Same lazy model as FactionsUUID ([MemoryFPlayer.java L790-L810](https://github.com/SaberLLC/Saber-Factions/blob/aa523f90ab/factions-shared/src/main/java/com/massivecraft/factions/zcore/persist/MemoryFPlayer.java#L790-L810)), plus `PowerRegenEvent`.

**Persistence — the cautionary tale.** `SaveTask` is scheduled with `runAsyncRepeating` ([MPlugin.java L102-L105](https://github.com/SaberLLC/Saber-Factions/blob/aa523f90ab/factions-shared/src/main/java/com/massivecraft/factions/zcore/MPlugin.java#L102-L105)), so `forceSave(false)` serialises live `HashMap`s of live faction objects off the main thread with no snapshot. The MySQL backend ignores the `sync` flag entirely and `saveCore()` does `connection.setAutoCommit(false); DELETE FROM board; INSERT ... addBatch()` for every claim, then commits ([MySQLBoard.java L78-L110](https://github.com/SaberLLC/Saber-Factions/blob/aa523f90ab/factions-shared/src/main/java/com/massivecraft/factions/zcore/persist/mysql/MySQLBoard.java#L78-L110)); `MySQLFactions` does the same `DELETE FROM factions` + reinsert ([MySQLFactions.java L35-L41, L124-L133](https://github.com/SaberLLC/Saber-Factions/blob/aa523f90ab/factions-shared/src/main/java/com/massivecraft/factions/zcore/persist/mysql/MySQLFactions.java#L35-L41)). A rollback on any SQL error is the only safety. With 10k claims that is a 10k-row transaction every save, and any concurrent mutation during iteration is a `ConcurrentModificationException` → rollback → **nothing saved that cycle**. Tracker: [#159 "faction disappears after restart"](https://github.com/SaberLLC/Saber-Factions/issues/159), [#160 "180 factions deleted on restart, 'Removing dead factions'"](https://github.com/SaberLLC/Saber-Factions/issues/160) (answer: "reset your JSON files").

**Listener surface additions over FactionsUUID.** `FactionsBlockListener`: `HangingBreakByEntityEvent` (item frames), `EntityChangeBlockEvent` for falling blocks and farmland trampling ([#249: the farmland handler fires for redstone ore state changes and spams](https://github.com/SaberLLC/Saber-Factions/issues/249)); `FactionsEntityListener`: `EntityDamageByEntityEvent` (bow hits), `PlayerShearEntityEvent`, `PlayerInteractEntityEvent`; `FactionsPlayerListener`: `PlayerInteractEvent` for bone meal and pearls, `AsyncPlayerChatEvent` (deprecated on Paper 26.1.2 in favour of `io.papermc.paper.event.player.AsyncChatEvent`, [AsyncPlayerChatEvent.java @ ver/26.1.2 L29-L33](https://github.com/PaperMC/Paper/blob/ver/26.1.2/paper-api/src/main/java/org/bukkit/event/player/AsyncPlayerChatEvent.java#L29-L33)); `ChorusFruitListener` uses `TeleportCause.CHORUS_FRUIT`, which is `@Deprecated(since="1.21.5", forRemoval=true)` in favour of `CONSUMABLE_EFFECT` ([PlayerTeleportEvent.java @ ver/26.1.2 L142-L148](https://github.com/PaperMC/Paper/blob/ver/26.1.2/paper-api/src/main/java/org/bukkit/event/player/PlayerTeleportEvent.java#L142-L148)); `SpawnerChunkListener`: `BlockPlaceEvent` (spawner-per-chunk limits, SPEC §28).

**Bugs 2021-2025**: save/restart data loss (above); ["takes the power of my ticks" timings](https://github.com/SaberLLC/Saber-Factions/issues/157) (chunk loading in claim/teleport paths); [#204 armour dupe via right-click armor swap with AdvancedEnchantments](https://github.com/SaberLLC/Saber-Factions/issues/204) (feature interaction with another plugin's inventory handling); [#267 GUI detection by `InventoryView#getTitle()` is spoofable via anvil rename](https://github.com/SaberLLC/Saber-Factions/issues/267) (must use a custom `InventoryHolder`); [#276 `/f sethome` withdraws money before validating the location](https://github.com/SaberLLC/Saber-Factions/issues/276); [#206 autoclaim flips to wilderness](https://github.com/SaberLLC/Saber-Factions/issues/206); [#217 neutral factions could build (perm defaults)](https://github.com/SaberLLC/Saber-Factions/issues/217); version-bump breakage on nearly every Minecraft release ([#210](https://github.com/SaberLLC/Saber-Factions/issues/210), [#214](https://github.com/SaberLLC/Saber-Factions/issues/214), [#228](https://github.com/SaberLLC/Saber-Factions/issues/228), [#277](https://github.com/SaberLLC/Saber-Factions/issues/277), [#292](https://github.com/SaberLLC/Saber-Factions/issues/292)).

### MassiveCraft Factions 2.x (historical, archived 2019)

The original. Everything is a MassiveCore `Entity` in a `Coll` (collection) backed by JSON flatfile or MongoDB.

**Claims.** `BoardColl` holds one `Board` entity **per world**; `Board.map` is a `ConcurrentSkipListMap<PS, TerritoryAccess>` where `PS` is a generic "physical state" object normalised with `ps.getChunkCoords(true)` on every lookup ([Board.java L45-L80](https://github.com/MassiveCraft/Factions/blob/808782376d/src/com/massivecraft/factions/entity/Board.java#L45-L80)). `TerritoryAccess` bundles host faction id + per-claim grants. Because the whole world's board is one entity, any single claim change calls `this.changed()` and the entire world map is re-serialised on the next sync tick. Users reported [#1350 "extreme lag when claiming"](https://github.com/MassiveCraft/Factions/issues/1350).

**Power.** `TaskPlayerPowerUpdate` runs every `taskPlayerPowerUpdateMinutes` over **online** players only and adds `powerPerHour × interval` ([TaskPlayerPowerUpdate.java](https://github.com/MassiveCraft/Factions/blob/808782376d/src/com/massivecraft/factions/task/TaskPlayerPowerUpdate.java)). It contains a real bug: inside the `for (Player player : ...)` loop, the "territory forbids power gain" and "world forbids power gain" branches `return` instead of `continue`, so the first player standing in a no-powergain zone silently ends regen for everyone after them in iteration order — matching the open ticket [#1294 "Powergain doesn't work correctly with world exceptions"](https://github.com/MassiveCraft/Factions/issues/1294). Death loss lives in `EnginePower.powerLossOnDeath(PlayerDeathEvent)` and explicitly guards against duplicate death events in the same tick ("other plugins can cause death event to fire twice") ([EnginePower.java L32-L60](https://github.com/MassiveCraft/Factions/blob/808782376d/src/com/massivecraft/factions/engine/EnginePower.java#L32-L60)). [#1330 `/f powerboost NaN`](https://github.com/MassiveCraft/Factions/issues/1330): an unvalidated double made Gson refuse to serialise the entity and the whole collection sync threw every tick.

**Relations.** `MassiveMapDef<String, Rel> relationWishes` per faction, same less-friendly-wins rule via `RelationUtil.getRelationOfThatToMe`. Per-faction `MFlag`s (explosions, firespread, endergrief, zombiegrief, powerloss, powergain, pvp, monsters, animals, ...) and `MPerm`s (build, door, container, ... per `Rel`) are the flag/perm split later plugins copied.

**Persistence.** `Entity.changed()` marks the entity; `Coll.onTick` → `syncIdentified()` saves marked entities ([Coll.java L783-L858](https://github.com/MassiveCraft/MassiveCore/blob/d80749a043/src/com/massivecraft/massivecore/store/Coll.java#L783-L858)). When local polling is enabled, change detection is done by re-serialising every entity to a `JsonObject` and diffing against `lastRaw` ([Coll.java L474-L502](https://github.com/MassiveCraft/MassiveCore/blob/d80749a043/src/com/massivecraft/massivecore/store/Coll.java#L474-L502)) — elegant, but O(total data) per poll. Hand-edited config JSON with a syntax error prevented the plugin from loading ([#1198](https://github.com/MassiveCraft/Factions/issues/1198)).

**Listener surface** (one `Engine*` class per concern — the cleanest decomposition of the old generation): `EnginePermBuild` (BlockBreak, BlockPlace, BlockDamage, HangingBreakByEntity, HangingPlace, SignChange, EntityDamageByEntity for entities, PlayerInteract for fire, BlockFromTo, BlockPistonExtend/Retract, EntityCombustByEntity, PlayerInteract use-block/use-item, PlayerInteractEntity, PlayerBucketEmpty/Fill); `EngineCanCombatHappen` (EntityDamageByEntity, EntityCombustByEntity, PotionSplash); `EngineFlagExplosion` (EntityExplode, EntityChangeBlock, EntityDamage, HangingBreak; `BlockExplodeEvent` was missing until [#1254](https://github.com/MassiveCraft/Factions/issues/1254)); `EngineFlagFireSpread` (BlockBurn, BlockIgnite, BlockSpread) — the **only** legacy plugin with fire spread protection; `EngineFlagEndergrief` (EntityChangeBlock); `EngineFlagZombiegrief` (EntityBreakDoorEvent); `EngineFlagSpawn` (CreatureSpawn); `EngineExploit` (ender pearl clipping, obsidian generators, portal traps, TNT waterlog); `EngineMoveChunk` (PlayerMove); `EngineTerritoryShield` (damage reduction in own land); `EngineTeleportHomeOnDeath`.

### ImprovedFactions (ToberoCat) — active, GPL-3.0

Kotlin + Exposed ORM, supports H2/SQLite/MySQL. Notable for *what not to do* with a database.

- Claims are a table `faction_claims(chunk_x, chunk_z, faction_id, world, zone_type, cluster_id)` ([FactionClaims.kt](https://github.com/ToberoCat/ImprovedFactions/blob/76b2d992f0/improved-factions/src/main/kotlin/io/github/toberocat/improvedfactions/claims/FactionClaims.kt)) and **every lookup is a query**: `Chunk.getFactionClaim()` → `FactionClaim.find { chunkX eq x and chunkZ eq z and world eq name }.firstOrNull()` ([FactionClaimHandler.kt L7-L15](https://github.com/ToberoCat/ImprovedFactions/blob/76b2d992f0/improved-factions/src/main/kotlin/io/github/toberocat/improvedfactions/claims/FactionClaimHandler.kt#L7-L15)). `ClaimTntListener` wraps the whole `blockList()` walk in one `loggedTransaction` and queries per block ([ClaimTntListener.kt](https://github.com/ToberoCat/ImprovedFactions/blob/76b2d992f0/improved-factions/src/main/kotlin/io/github/toberocat/improvedfactions/listeners/claim/ClaimTntListener.kt)). Result: [#287](https://github.com/ToberoCat/ImprovedFactions/issues/287)/[#328 "Extreme lag with sqlite and h2 … if claiming more than render distance crashes server"](https://github.com/ToberoCat/ImprovedFactions/issues/328), both open; a MySQL column-type mismatch made MySQL unusable in the same reports.
- Listener decomposition is the most granular of any plugin: one small class per (event × zone-type), instantiated once per configured zone and enabled per `protection.<namespace>` config key ([ClaimProtectionListener.kt](https://github.com/ToberoCat/ImprovedFactions/blob/76b2d992f0/improved-factions/src/main/kotlin/io/github/toberocat/improvedfactions/listeners/claim/ClaimProtectionListener.kt)). Events covered: BlockPlace, BlockBreak, PlayerInteract (blocks, trampling, spawn eggs), PlayerInteractEntity, HangingBreakByEntity, PlayerArmorStandManipulate, **ProjectileHitEvent**, **VehicleDamageEvent**, EntityExplode (TNT, "full TNT", creeper), **EntityPlaceEvent** (end crystals — added after [#181](https://github.com/ToberoCat/ImprovedFactions/issues/181)), PlayerBucketEmpty/Fill/**PlayerBucketEntityEvent**, EntityDamageByEntity split by target class (animal/villager/golem/monster/boss/armor-stand), CreatureSpawn, EntityChangeBlock.
- Explosion semantics bugs: [#321 border explosions never cross a chunk edge, so flat walls on a chunk border are unbreakable](https://github.com/ToberoCat/ImprovedFactions/issues/321) (open) and [#196 cannons can hit safezones](https://github.com/ToberoCat/ImprovedFactions/issues/196) (fixed with an "any TNT damage in zone" flag). Power: [#180](https://github.com/ToberoCat/ImprovedFactions/issues/180)/[#355 power lost for deaths outside whitelisted worlds](https://github.com/ToberoCat/ImprovedFactions/issues/355) (regressed twice).

### Medieval Factions 5.x (Dans-Plugins) — active, GPL-3.0

Kotlin, jOOQ, Flyway migrations, H2 or MySQL, repository/service layering close to what SPEC §6 asks for. Different gameplay (feudal, no raid-by-TNT), but its data layer is the closest prior art to Avian's DB design and its recent issues are unusually well-diagnosed.

- Claims: `MfClaimService` loads all rows at boot into `ConcurrentHashMap<ClaimKey(worldUUID, x, z), MfClaimedChunk>` and every read is the map ([MfClaimService.kt L9-L30](https://github.com/Dans-Plugins/Medieval-Factions/blob/ed3faa9cb1/src/main/kotlin/com/dansplugins/factionsystem/claim/MfClaimService.kt#L9-L30)); writes upsert the repository and then update the map ([L154-L170](https://github.com/Dans-Plugins/Medieval-Factions/blob/ed3faa9cb1/src/main/kotlin/com/dansplugins/factionsystem/claim/MfClaimService.kt#L154-L170)). `getClaims(factionId)` filters all claims (no reverse index).
- Power: a scheduled "power cycle" issues two set-based SQL `UPDATE`s (online players gain along a curve, offline lose), then re-reads and notifies on the main thread ([MedievalFactions.kt L604-L640](https://github.com/Dans-Plugins/Medieval-Factions/blob/ed3faa9cb1/src/main/kotlin/com/dansplugins/factionsystem/MedievalFactions.kt#L604-L640), [JooqMfPlayerRepository.kt L48-L70](https://github.com/Dans-Plugins/Medieval-Factions/blob/ed3faa9cb1/src/main/kotlin/com/dansplugins/factionsystem/player/JooqMfPlayerRepository.kt#L48-L70)). Migration `V4__Store_power_at_logout.sql` shows they moved to snapshotting power at logout.
- Threading bugs, all 2026: [#2014 `PlayerQuitEvent` → `MfPlayerService.save` → jOOQ upsert on the main thread; watchdog killed the server after 60 s on a slow H2](https://github.com/Dans-Plugins/Medieval-Factions/issues/2014); [#2006/#2020/#2021 async tasks reading `player.location`/`world`/health off the main thread](https://github.com/Dans-Plugins/Medieval-Factions/issues/2006); [#1981 unregistered player on a pressure plate queued one async save per tick](https://github.com/Dans-Plugins/Medieval-Factions/issues/1981); [#2017 optimistic lock `WHERE version = version` is a tautology — last write wins](https://github.com/Dans-Plugins/Medieval-Factions/issues/2017).
- Protection bugs: [#1868 hoppers pull from locked chests](https://github.com/Dans-Plugins/Medieval-Factions/issues/1868) → they now hook `InventoryMoveItemEvent` and resolve `DoubleChest` halves ([InventoryMoveItemListener.kt](https://github.com/Dans-Plugins/Medieval-Factions/blob/ed3faa9cb1/src/main/kotlin/com/dansplugins/factionsystem/listener/InventoryMoveItemListener.kt)); [#1957 standing on a pressure plate sends a deny message every tick](https://github.com/Dans-Plugins/Medieval-Factions/issues/1957); [#1838 gate mechanics dupe any block that breaks without support (bamboo, scaffolding, torches)](https://github.com/Dans-Plugins/Medieval-Factions/issues/1838); [#1996 entity protection only covered villagers and armor stands](https://github.com/Dans-Plugins/Medieval-Factions/issues/1996); [#1960 horses deleted when logging out while riding in a claim](https://github.com/Dans-Plugins/Medieval-Factions/issues/1960).
- Listener surface: one class per event — BlockBreak, BlockPlace, **BlockBurn**, BlockExplode, EntityExplode, PistonExtend/Retract, PlayerInteract, PlayerInteractEntity, **PlayerInteractAtEntity**, PlayerBucket, **InventoryMoveItem**, InventoryClick, EntityDamage, EntityDamageByEntity, PotionSplash, **LingeringPotionSplash**, **AreaEffectCloudApply**, CreatureSpawn, PlayerDeath, PlayerMove, PlayerTeleport, AsyncPlayerPreLogin, AsyncPlayerChat (deprecated on Paper).

### AlpineFactions (alpine-network) — MPL-2.0

Java, small, recent. Two ideas worth noting: (1) claims are partitioned into `ClaimRegion`s of 32×32 chunks per world, each with its own dirty flag, so a save touches only regions that changed ([ClaimRegion.java](https://github.com/alpine-network/alpine-factions/blob/93af6cf839/factions/src/main/java/co/crystaldev/factions/store/claim/ClaimRegion.java), [ClaimStore.java L150-L165](https://github.com/alpine-network/alpine-factions/blob/93af6cf839/factions/src/main/java/co/crystaldev/factions/store/claim/ClaimStore.java#L150-L165)) — though the region key is a `String` built per lookup, which undoes some of the benefit; (2) `PowerEngine` uses a Paper `ServerTickEvent` with `event.isTime(1, MINUTES)` gating, but then iterates every cached player and calls `players.save(player)` each minute ([PowerEngine.java](https://github.com/alpine-network/alpine-factions/blob/93af6cf839/factions/src/main/java/co/crystaldev/factions/engine/PowerEngine.java)) — the "scan everything on a timer" anti-pattern SPEC §64 forbids. Listener surface: `InteractionEngine` (BlockBreak, BlockPlace, **BlockMultiPlaceEvent**, BlockDamage, BucketEmpty/Fill, HangingBreakByEntity, HangingPlace, PlayerInteract, SignChange), `PhysicsEngine` (EntityDamageByEntity, BlockExplode, EntityExplode, PistonExtend/Retract), `CombatEngine` (EntityDamageByEntity, EntityCombustByEntity, PotionSplash), `PlayerEngine` (Login, Quit, Move, Teleport).

## Consolidated protection-event checklist

Legend: F = FactionsUUID legacy, U = FactionsUUID 4.x, S = Saber, M = MassiveCraft, X = FactionsX, I = ImprovedFactions, D = Medieval, A = Alpine. "Avian" column is the recommendation for `avian-factions` on Paper 26.1.2 (all listed events exist and are non-deprecated in paper-api `ver/26.1.2` unless noted).

| `entity.EntityDamageEvent` / `entity.EntityDamageByEntityEvent` | PvP gating by relation, safezone invulnerability, item frames / armor stands / paintings / minecarts as damageable "blocks", pets; resolve `Projectile#getShooter()`; use `getDamageSource()` (1.20.4+) rather than synthetic events | F U S M X I D A | must |

## Recurring bug classes across trackers (2023–2026 weighted)

1. **Protection-surface holes** (every tracker, the majority of "bug" tickets): a new block/entity/mechanic Minecraft adds (wind charges, end crystals, lecterns, glow item frames, silverfish, bamboo/scaffolding physics, honey/slime + pistons) that the listener set never covered. Root cause: protection written as N special-case listeners instead of "one decision function × exhaustive event table", and no regression test per event.
2. **Decision-function regressions** ([UID #42](https://github.com/FactionsU/UID/issues/42), [#55](https://github.com/FactionsU/UID/issues/55), [Saber #217](https://github.com/SaberLLC/Saber-Factions/issues/217), [IF #180/#355](https://github.com/ToberoCat/ImprovedFactions/issues/355)): early `return`s and config short-circuits ordered wrongly, so wilderness/safezone/world-whitelist branches are skipped. Root cause: nested if-chains mixing territory type, relation, config flags and bypass mode in one method.
3. **Persistence data loss** ([FUUID #1403](https://github.com/drtshock/Factions/issues/1403), [Saber #159/#160](https://github.com/SaberLLC/Saber-Factions/issues/160), [MC #1198/#1330](https://github.com/MassiveCraft/Factions/issues/1330)): non-atomic whole-file writes; "empty = fresh" load semantics; startup cleaners that delete orphans; unvalidated doubles (NaN) poisoning serialisation; async serialisation of live mutable state.
4. **Main-thread I/O and O(n) scans** ([IF #287/#328](https://github.com/ToberoCat/ImprovedFactions/issues/328), [Medieval #2014](https://github.com/Dans-Plugins/Medieval-Factions/issues/2014), [UID #46](https://github.com/FactionsU/UID/issues/46), [Saber #140/#157](https://github.com/SaberLLC/Saber-Factions/issues/157), [MC #1350](https://github.com/MassiveCraft/Factions/issues/1350)): DB query per event, DB write on quit, F-top computed synchronously, Dynmap re-render on every claim, per-minute save-everything loops.
5. **Async code touching Bukkit state** ([Medieval #2006/#2020/#2021](https://github.com/Dans-Plugins/Medieval-Factions/issues/2006)): reading `Player#getLocation()`/`World` inside async tasks.
6. **Message and task spam from per-tick physical events** ([Medieval #1957/#1981](https://github.com/Dans-Plugins/Medieval-Factions/issues/1981), [Saber #249](https://github.com/SaberLLC/Saber-Factions/issues/249)): `PlayerInteractEvent` with `Action.PHYSICAL` and `EntityChangeBlockEvent` fire every tick; deny messages and side-effects must be rate-limited.
7. **Economy ordering** ([Saber #276](https://github.com/SaberLLC/Saber-Factions/issues/276), [FUUID #1363](https://github.com/drtshock/Factions/issues/1363)): withdraw before validate; unreproducible balance loss with no transaction log (SPEC §6 requires an `economy_transactions` ledger).
8. **Spoofable GUI identification** ([Saber #267](https://github.com/SaberLLC/Saber-Factions/issues/267)): matching `InventoryView#getTitle()`; players can name a chest to match. Use a custom `InventoryHolder`.
9. **Version-bump breakage** (Saber's tracker is mostly this): version-specific listener shims (`OneEightPlusListener`, `PortalListener_114`, `factions-modern` module), renamed enum constants, deprecated constructors. Pinning Paper 26.1.2 and refusing reflection/NMS makes this a compile-time problem rather than a runtime one.
10. **Index desync** ([UID #41](https://github.com/FactionsU/UID/issues/41), [Saber #206](https://github.com/SaberLLC/Saber-Factions/issues/206)): forward map and reverse (faction→claims) map updated in different places.

## Lessons for Avian (`avian-factions`)

Mapped to SPEC sections. "Do" items are patterns observed working; "don't" items each cite a tracker failure above.

**Claims (§9, §64)**
- DO keep the chunk→faction index entirely in memory, one structure per world, keyed by a packed `long` (Morton or `(x << 32) | (z & 0xffffffff)`) mapping to a compact faction id (`int` surrogate; the UUID lives on the faction row). Maintain the reverse index `factionId → LongSet` in the same two methods (`claim`, `unclaim`) and nowhere else. MariaDB is the durable store and is loaded once at boot; it is never on the read path. (UID `WorldTracker`; Medieval `MfClaimService`.)
- DO expose exactly one lookup, `Territory at(World, chunkX, chunkZ)`, that returns a non-null object (wilderness singleton) so callers never null-check. Provide `at(Location)`/`at(Block)` overloads that do `>> 4` inline without allocating a key object.
- DO count claims per faction from the reverse index (O(1)), not by scanning (legacy `getAllClaims`, FactionsX, Medieval). Claim capacity = `floor(power / powerPerClaim)` compares against that count.
- DON'T query the database per event (ImprovedFactions), and DON'T store a whole world's claims as one serialised blob that is rewritten on each change (MassiveCraft). Persist claim changes as single-row upserts/deletes queued to an async writer.
- DO test the claim index against the raiding invariants: overclaim, unclaim-all, disband, world unload, and "index and reverse index agree" after each.

**Explosions and TNT (§25–26)**
- DO implement one `handleExplosion(origin, source, blockList, result)` shared by `EntityExplodeEvent` and `BlockExplodeEvent`: (1) decide the origin chunk; (2) collect distinct chunks of `blockList()` into a small `LongSet`; (3) decide once per chunk; (4) `removeIf` blocks whose chunk was denied. Cost is O(blocks) hash lookups + O(distinct chunks) decisions, no allocation per block. (FactionsUUID.)
- DO make the decision a pure function `deny(source kind, territory kind, faction online?, raid state, shield window)`; source kinds: TNT/minecart, creeper, fireball/wither, wind charge, other. Branch on `getExplosionResult()` for wind charges. Cross-border explosions must be *allowed* into a raidable claim from wilderness, or you get IF #321's unbreakable chunk-border walls.
- DO handle the waterlog rule (`TNT in liquid breaks the six neighbours below blast resistance 100`) as a configurable option; it is the standard anti-waterwall mechanic.
- DON'T call "is anyone online" by scanning `getOnlinePlayers()` per decision; keep an online-member counter per faction updated on join/quit/leave/kick.

**Power (§8)**
- DO store per player `power`, `powerBoost`, `lastPowerUpdateAt` and compute regen/offline decay lazily on read from elapsed time, clamped to `[min, max]`. Freeze regen while dead, in combat/AFK if desired, or when the faction is frozen. Persist on quit (async) and periodically. Faction power = sum over members on demand, cached for the current tick if the sum is hot. This satisfies "do not run unnecessary work every tick" with zero scheduled work. (FactionsUUID/Saber/FactionsX.)
- DO apply death loss from `PlayerDeathEvent` with a same-tick duplicate guard (MassiveCraft learned this from other plugins double-firing) and a world/territory whitelist checked *before* the deduction (IF #180/#355).
- DON'T write a periodic loop over all players/factions that saves each one (Alpine `PowerEngine`), and if you do have a loop, `continue`, never `return` (MassiveCraft `TaskPlayerPowerUpdate`).
- DO validate every numeric admin input (`NaN`, infinity, negatives) at the command layer (MC #1330).

**Relations (§7, §9)**
- DO model relations as per-faction "wishes" (`Map<factionId, Relation>`) and derive the effective relation as the less friendly of the two wishes; enemy is unilateral, ally/truce need both. Provide an ordered `Relation` enum with `isAtLeast`. Cache nothing; the lookup is two map gets.
- DO route every protection check through `relation(actorFaction, territoryFaction)` + `raidState(territoryFaction)` and keep the per-territory flags (explosions, fire spread, mob spawn, pvp) separate from per-relation permissions (build, container, door, hopper) — the MassiveCraft `MFlag`/`MPerm` split that every successor kept.
- DO fire an event on relation change so scoreboard/tab/map (§40–41) update, and log it (§66).

**Persistence (§6, §65, §75)**
- DO write through repository interfaces with single-row upserts on change, batched by an async writer with a bounded queue; never a full-table `DELETE`+`INSERT` (Saber MySQL) and never a blocking write in a join/quit/interact listener (Medieval #2014, #1981).
- DO snapshot on the main thread and serialise/write off it (UID `JSONFactions`), never hand live mutable objects to an async serialiser (Saber, UID `JSONFPlayers`).
- DO treat "0 rows loaded but the tables exist" as a normal boot but treat any load *error* as fatal (disable the module, do not start cleaners). DON'T ship a boot-time "remove orphan claims/players" cleaner that runs unconditionally (FactionsUUID `Board.clean()`); make it an admin command with a dry-run.
- DO version rows and make the optimistic-lock predicate `WHERE id = ? AND version = <expected>` with a test that proves it fails on a stale write (Medieval #2017).
- DO keep an immutable audit table for claim/relation/power/bank changes (SPEC §66), because "bank cleared for no reason" (FUUID #1363) is unanswerable without it.

**Protection listeners (§9, §74)**
- DO hook the union in the checklist above (all "must" rows) from day one; add a regression test per event that asserts deny for enemy/neutral and allow for member/ally/bypass, plus wilderness and safezone/warzone cases (UID #42/#55 were both missing-case regressions).
- DO put the decision in one place: a `ProtectionPolicy` with pure methods `canBuild(actor, territory)`, `canUse(actor, territory, kind)`, `canDamage(actor, target)`, `denyExplode(...)`, ordered as: world enabled → bypass → territory type (wilderness/safezone/warzone) → raid/shield state → relation/role permission. Listeners only translate events into those calls. (UID `Protection`.)
- DON'T construct synthetic Bukkit events to reuse checks (legacy FactionsUUID, MassiveCraft); on 26.1.2 those constructors are deprecated for removal and it hides the real cause. Use `EntityDamageEvent#getDamageSource()` and `Projectile#getShooter()` to attribute damage.
- DO rate-limit deny feedback per player (one message per N seconds per reason) because `PlayerInteractEvent(PHYSICAL)`, `EntityChangeBlockEvent` and `InventoryMoveItemEvent` fire every tick.
- DO identify Avian GUIs by a custom `InventoryHolder` (and items by PDC), never by title (Saber #267).
- DO withdraw money only after every precondition passed, inside the same transaction as the state change (Saber #276).

**Process**
- DO pin Paper 26.1.2 and compile with `-Werror` on deprecation for `org.bukkit.event` types; the studied plugins' version pain came from shims and renamed constants (`PotionEffectType.CONFUSION` → `NAUSEA`, `TeleportCause.CHORUS_FRUIT` → `CONSUMABLE_EFFECT`, `AsyncPlayerChatEvent` → `AsyncChatEvent`, `com.destroystokyo…TNTPrimeEvent` → `org.bukkit.event.block.TNTPrimeEvent`).
- DO keep F-top (§11) and any Vault balance aggregation on an async schedule with a cached result (UID #46).
- DO keep the map renderer (§9 `/f map`, Dynmap-style integrations) off the claim-change path; mark dirty and re-render on a timer (Saber #140).
